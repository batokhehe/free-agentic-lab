+### Same origin
+
+The browser only ever calls the relative path `/api/v1`. In production the reverse proxy routes `/api/v1/*` to the Go API and everything else to Next.js, under one HTTPS origin. In development the Next.js dev server forwards `/api/v1/*` to `http://127.0.0.1:8080` with a rewrite that exists only when `NODE_ENV=development`. The API grants no CORS and Next.js is never a proxy or BFF in production.
+
+### Server and client components
+
+Authenticated data is fetched in the browser: the access token exists only in browser memory and the refresh cookie is scoped to `/api/v1/auth`, so a server component can never hold credentials. Server components are used for the static shell, layout and non-authenticated static content only. `app/providers.tsx` is the client boundary (one `QueryClient` per tab).
+
+### API client and types
+
+`lib/api/client.ts` is a handwritten `fetch` client: relative `/api/v1` paths built from encoded segments (`apiPath`), queries through `URLSearchParams`, `AbortSignal`, `credentials: "same-origin"`, the Bearer token from an injected token source, and no logging. A 401 asks the token source to renew once and the original request is retried at most once; an anonymous request never renews. Failures become a typed `ApiError` (`kind`, `status`, `code`, `requestId`, `details`, `retryAfterMs`) read from the API error envelope; the server's message is kept for diagnostics only and is never UI copy, and no error code is invented when there is no envelope.
+
+`lib/api/types.ts` holds handwritten types matching the backend contract, with every nullable field typed `| null`. They are not generated from `docs/api/openapi.yaml`, which declares OpenAPI 3.1 but marks nullable fields with the 3.0 `nullable: true` keyword; correcting that is a separate API-contract follow-up. Fields the API never returns (worker lease, heartbeat, stored error message, snapshots) are not declared.
+
+### Authentication foundation
+
+`lib/auth/session.ts` keeps the access token in a closure, never in browser storage and never in the state snapshot given to React. `lib/auth/refresh.ts` renews it: concurrent renewals in a tab share one refresh; across tabs a refresh runs only while holding the Web Lock `sentinel-auth-refresh`, so no two refreshes of the shared refresh cookie are ever in flight (the backend revokes a rotated session and revokes the whole lineage on reuse); the refreshing tab publishes the new token, and any logout or lost session, on the BroadcastChannel `sentinel-auth`. Without Web Locks nothing is refreshed and the session expires. The refresh request is `POST /api/v1/auth/refresh` with `X-Requested-With: XMLHttpRequest`, the cookie travelling only as an HttpOnly cookie. Login, the boot-time session restore and protected routes are Stage 1.
+
+### Data fetching
+
+TanStack Query, with defaults in `lib/api/query-client.ts`: network and 5xx failures retry after 5s, 10s, 20s and 40s (±20% jitter, at most 60s), a 429 after its `Retry-After`, nothing else; queries do not poll in a hidden tab and refetch once when it is visible again; mutations are not retried. Scan polling intervals (5s for a running scan, 10s for the first page of a list with running scans) are applied in Stage 6.
+
+### Lint and security checks
+
+ESLint forbids `console`, `localStorage`, `sessionStorage` and `document.cookie` in application code. `test/security.test.ts` checks the browser sources for storage, cookie and console use and for absolute URLs, checks that the API types declare no internal field, and that the `/api/v1` rewrite exists only in development.
+
+### Stages
+
+Stage 0 (this foundation) precedes Stage 1 Authentication, Stage 2 Project Dashboard, Stage 3 Project/Assets, Stage 4 Scope, Stage 5 Scan Creation and Stage 6 Scan Monitoring, in that order.
